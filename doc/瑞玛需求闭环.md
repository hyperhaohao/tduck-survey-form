# 瑞玛需求闭环开发与运行说明

本分支基于官方社区版增加需求征集、处理、结果查询、内部公示，以及 AI 建表与设计器协作。**已部署独立 240 测试实例，入口 http://192.168.1.240:18000；真实员工登录、MySQL 接口闭环、实际填报和附件上传已通过。** 原 15000 填鸭实例继续保留。

## 一、功能与权限

- 默认登录填写，收集单可显式开放匿名填写。匿名业务记录不关联登录账户，提交后只领取一次查询码。
- 人员能力取并集：普通填报者、收集单经办人、单据管理员、平台单据管理者、组织架构管理者、用户管理者、全局管理员可同时属于同一账户。
- 平台能力分三项，由全局管理员按用户授予：单据管理（`form.manage`，含新建收集单、设计发布与 AI 协作）、组织架构（`org`，含部门主管设置）、用户管理（`user.manage`，不含重置密码）。全局管理员=原系统超级管理员+`ruima.demand.admin-ids`，看全部收集单；非全局管理者从「单据管理」页 `/demand/manage` 工作，仅看本人创建或 `can_manage` 的收集单。单据成员权限“管理”（`can_manage`）只能管理本收集单，不能新建收集单、设计发布或使用 AI。后台管理 `/demand/admin` 仅全局管理员可见；原后台在需求模式下同时受服务端权限限制。表单级提交、回收、通知、分享、数据推送设置随该收集单的管理权限开放；原表单后台（我的项目）入口、原表单数据、报表、回收站等仍仅全局管理员可用，拥有单据管理能力的用户通过“新建收集单/设计与发布”进入原表单设计器。
- 收集单可作废/恢复：作废后停止新填报并从员工入口隐藏，已有需求、处理记录和公示保留；恢复后按原收集配置继续开放。删除原表单仍走原回收站规则，不自动清理需求数据。单据管理员或全局管理员可删除单条需求：删除需求、消息、已读和公示，原答卷保留在原表单数据中。
- 收集单可设为“只收集”：不进入正式回复、采纳与公示；需求未读时计入待我处理，打开详情标记已读后移出待办，角标同步减少。详情隐藏全部处理区，仍可查看提交内容；`read` 与删除保留，回复/采纳/分派/追问/发布接口拒绝。
- 首页收集单可见范围跟随填报与成员权限：`LOGIN` 对所有登录用户可见可填；`SELECTED` 对 `can_fill`、`can_handle`、`can_manage` 任一成员可见，但只有 `can_fill` 能填报；非填报成员卡片显示“查看需求”，进入待我处理或获授权总表。
- 超级管理员可将任意收集单删除到全局回收站并恢复；删除为逻辑删除，需求、答卷与附件保留；彻底删除仅限无需求、无答卷的表单，且仅超级管理员可执行。
- 经办人可查看获授权总表，仅处理当前分派给自己的需求。单据管理员由成员权限“可管理/可公示”授予，创建人默认拥有且每个收集单至少保留一名；可在「单据管理」页或待我处理查看本收集单全部未办结需求、分派经办、代填采纳与实施结果，并发布或跳过公示。全局管理员对所有收集单拥有同等能力。部门主管为 `rm_demand_dept.leader_id` 标识，当前不自动授予权限，后续可用于部门领导审核。
- 采纳后跟踪待实施、实施中和已完成；暂缓保留待办，不采纳结束处理。
- 正式回复立即对填报者可见，内部备注及草稿不向填报者返回。登录填报者可在详情中追加追问；追问会让需求重新进入经办人和单据管理员的待办，只有新的正式回复才清除追问。匿名需求不支持在线追问。
- 公示快照由全局管理员或该收集单的单据管理员审核发布，发布前必须有明确的采纳结果（采纳/暂缓/不采纳），正式回复为选填，内部备注和草稿不能替代公示快照；私有进度更新不自动改写已发布内容。选择“不公示”会记录状态并移出待办，之后可重新发布。
- 首页收集单由全局管理员拖动保存全局顺序，所有用户按该顺序看到；新建收集单默认排在最前；需求收集页不启用拖动。
- 待我处理的单据管理员范围只包含未办结且未公示、未跳过的需求；批量操作由前端逐条调用单条接口，按每条需求自己的版本校验，部分失败不回滚并汇总提示。
- AI 智能建表与设计器协作随平台「单据管理」能力使用，AI 配置仅全局管理员。AI 生成的是普通表单，需在「单据管理/后台管理 → 收集单 → 收集配置」成为收集单，不自动发布或开放匿名。详见 [AI 建表与协作说明](AI建表与协作说明.md)。

## 二、运行准备

1. 在测试数据库按官方流程建立原社区版表结构；升级现有实例前先备份，不重新导入会删除旧表的官方初始化脚本。
2. 新环境首次执行 `doc/ruima-demand-schema.sql` 一次，仅新增 `rm_demand_*` 表。已有实例先备份，执行 `doc/migration-20261114-form-manager.sql` 一次后再部署新后端与前端；迁移新增 `can_manage`、`publication_skipped` 并为收集单创建人回填单据管理员，不可重复执行。平台能力细分需执行 `doc/ruima-demand-migration-20261125-capability.sql`（新建 `rm_demand_permission` 并迁移存量后台管理员），部门主管需执行 `doc/ruima-demand-migration-20261125-dept-leader.sql`（新增 `rm_demand_dept.leader_id`）；部署顺序为迁移、后端、前端。脚本中的独立索引不是重复迁移入口。
3. 复制 `tduck-api/src/main/resources/application-demand.example.yml` 到本机忽略文件，例如 `application-demand.local.yml`，以外部配置方式加载。
4. 按既有运行方式配置数据库、上传存储及原系统参数（当前社区版本使用 EHCache，本测试实例没有新增 Redis）；示例配置只补充需求模块和统一登录参数。
5. 启用 `ruima.demand.enabled` 后，原维护管理员可进入后台；额外管理员可通过配置或管理页面明确授权。统一登录环境可将指定 Casdoor 身份经 `rm_demand_identity` 显式映射到原系统超级管理员，见 240 部署说明。
6. 为本系统注册独立登录应用，禁止复用其他业务的客户端密钥。将密钥放在环境变量或本机忽略配置，不进入 Git、日志或文档。
- 2026-11-25 权限细分与部门主管已在 237 部署：4 个存量后台管理员迁移为 `form.manage`，组织架构/用户管理 0 个，需全局管理员补授；240 未更新。部署镜像、JAR、静态哈希、备份与报告见 [237部署说明](../deploy/237/README.md)。

```powershell
mvn -B -pl tduck-api -am test
mvn -B -pl tduck-api -am package
java -jar tduck-api/target/tduck-api.jar --spring.config.additional-location=file:./application-demand.local.yml
```

前端生产包可按原项目部署方式放入后端静态目录或由反向代理提供。同一入口需要分别转发业务接口与前端页面，并支持前端 History 路由回退；`/demand-api/*` 为接口，`/demand/*` 为前端页面，分别转发，避免直接刷新页面时收到 JSON。

## 三、独立登录应用

- 建议应用名：`app-ruima-survey`，显示名：瑞玛需求征集，组织：`ruima`。
- 采用授权码流程，启用 PKCE S256；关闭本应用自助注册，复用现有员工身份及登录方式。
- 本地回调示例：`http://localhost:8999/auth/oidc/callback`。测试服务器回调按实际统一入口配置，例如 `http://192.168.1.240:18000/auth/oidc/callback`。
- 回调地址采用精确白名单；手机访问时不得使用手机自身的 localhost 作为回调。
- 已只读核对现有签发地址为 `http://192.168.1.237:13004`，组织为 `ruima`。浏览器入口与签发地址可以分别配置，不能仅为公网入口而替换令牌 issuer。
- 校验签名、issuer、受众、有效期、nonce、组织及禁用标记。身份按 issuer 与 subject 映射，不通过姓名或邮箱自动合并账户，也不采信身份声明授予本地管理员权限。
- 登录回调只在地址片段中携带短时一次性票据，票据与 HttpOnly 浏览器 Cookie 绑定；原系统会话令牌不进入跳转地址。

## 四、接口与数据

- `/demand-api/capabilities`：模块开关、菜单能力与计数，含 `manage`。
- `/demand-api/forms`、`/demand-api/forms/{key}`：可见收集单与填报方式；已作废收集单不再返回员工入口。每行返回 `collectOnly`、`canFill`、`canHandle`、`canManage`，前端据此决定“填写”或“查看需求”。
- `/demand-api/forms/{key}/handlers`：单据管理员读取可分派的经办人，仅返回姓名与标识。
- `/demand-api/requests`：本人、待办、获授权总表与后台管理范围（`scope=managed`，仅后台管理员）；支持提交日期范围筛选，返回最近正式回复时间、公示状态、`followupPending`、`collectOnly` 及当前账户的 `canHandle`、`canManage`。只收集需求未读时进入待办，已读后不再进入。
- `/demand-api/requests/{id}/followup`：登录填报者本人对非匿名需求追加追问；写入 `FOLLOWUP` 消息并设置 `followup_at`，需求重新进入经办人/单据管理员待办；不增加填报者未读。详情返回 `canFollowUp` 与 `followupPending`。
- `/demand-api/requests/summary`：按收集单汇总当前范围的条数、未读与待办，口径与列表一致，并返回 `canManage`。
- `/demand-api/export/requests`、`/demand-api/export/publications`：按当前筛选条件导出 `.xlsx`，权限与列表一致，单次最多 10000 行；截断时响应头为 `X-Export-Truncated: true`。需求导出保留 9 列清单；单收集单按题目追加 `填报-<label>` 列、`填报人部门` 和 `其他填报内容`；`formKey` 为空时追加 `填报内容` 文本。内容来自原答卷 `original_data`，选择类优先显示 `xxxlabel`，附件导出名称和 URL，已删除/改名题目的旧键进入其他填报内容；公示导出仍只导出审核快照。
- `/demand-api/requests/{id}/delete`：单据管理员或全局管理员删除需求，清理消息、已读和公示；原答卷保留在原表单数据中，需求模块列表、待办、导出和角标不再出现该需求。
- `/demand-api/requests/{id}/publication`：审核发布或撤回，发布前须已有明确采纳结果（非待评估）；同级 `/publication/auto` 自动生成并发布，`/publication/skip` 记录不公示。只收集收集单不产生新公示，详情不返回处理区；历史公示保留，撤回仍可用。`/demand-api/publications/{id}/archive` 归档或恢复，`/demand-api/publications/{id}/delete` 逻辑删除（需求保留）；仅该收集单的单据管理员或全局管理员可操作。归档不计未读、不回待办；删除后需求回到待办并可重新发布或选择不公示。`/demand-api/publications` 默认不返回已归档、已删除和已删除收集单的公示，`includeArchived=true` 仅向有管理权限的账户补充已归档项。
- `/demand-api/lookup`：匿名查询，凭证放请求体并限速。
- `/demand-api/publications`：仅返回已审核的公示快照，并带所属收集单标识与名称、填报者、经办人及提报时间。
- 填报人部门：不再作为表单题目注入或展示。提交时服务端按登录人所属部门写入 `rm_demand.department` 快照（JSON 数组，匿名或无部门为 `["无"]`），详情返回 `department` 并固定显示第一行；存量需求由迁移从原答卷 `demandDept` 回填。组织架构、部门授权和成员名册保留。详情按表单字段顺序显示中文标签与选项文字。
- `/demand-api/admin/*`：后台管理员按本人创建或 `can_manage` 配置收集单与成员，全局管理员可管理全部；`/admin/forms/sort` 仅全局管理员保存首页收集单全局顺序（请求体 `formKeys`，未出现的收集单保持原位）；`POST /admin/forms/{key}` 支持 `collectOnly`（只收集）；`/admin/departments` 返回部门目录，`/admin/departments/members` 返回在职成员的部门归属（每个有效部门一条，未归属成员的 `deptKey` 为空）；`POST /admin/departments`、`PUT/DELETE /admin/departments/{deptKey}` 维护单个部门，`POST/DELETE /admin/departments/{deptKey}/members/{userId}` 增删成员，`PUT /admin/users/{userId}/departments` 整体设置成员部门，部门有下级、成员或收集单授权时拒绝删除；`/admin/forms/{key}/members[/{memberId}]` 与 `/admin/forms/{key}/department-members[/{deptKey}]` 维护成员和部门授权，`DELETE` 均校验最后一名有效单据管理员；`/admin/forms/{key}/void` 作废或恢复收集单，作废后停止新填报但保留需求历史；`/admin/forms/deleted`、`/{key}/delete`、`/{key}/restore`、`/{key}/purge` 提供全局回收站、逻辑删除、恢复与彻底删除；`/admin/roles` 仅全局管理员。
- `/auth/oidc/*`：登录起始、回调及一次性票据兑换。
- `/ai/*`：AI 状态、流式会话与测试连接；配置存 `sys_env_config.deepSeekEnvConfig`，权限、阶段与错误码见 [AI 建表与协作说明](AI建表与协作说明.md)。

原提交记录为需求正文唯一正本。处理索引、消息、已读版本、公示及身份映射放在新增表中。原提交接口与需求索引写入处于同一事务；处理结果和分派使用版本校验及行锁防止覆盖。需求索引新增 `publication_skipped` 记录不公示状态，`department` 保存提交时点部门快照；`rm_demand_form.sort_no` 保存首页全局顺序。私有附件通过需求授权下载接口读取，本地 `/u/<收集单摘要>/...` 静态路径拒绝绕过。

# 瑞玛需求闭环开发与运行说明

本分支基于官方社区版增加需求征集、处理、结果查询和内部公示。**已部署独立 240 测试实例，入口 http://192.168.1.240:18000；真实员工登录、MySQL 接口闭环、实际填报和附件上传已通过。** 原 15000 填鸭实例继续保留。

## 一、功能与权限

- 默认登录填写，收集单可显式开放匿名填写。匿名业务记录不关联登录账户，提交后只领取一次查询码。
- 人员能力取并集：普通填报者、收集单经办人、单据管理员、需求管理员可同时属于同一账户。
- 仅管理员创建和管理收集单；原后台在需求模式下同时受服务端权限限制。
- 经办人可查看获授权总表，仅处理当前分派给自己的需求。单据管理员由成员权限“可管理/可公示”授予，创建人默认拥有且每个收集单至少保留一名；可查看本收集单全部未办结需求、分派经办、代填采纳与实施结果，并发布或跳过公示。全局管理员对所有收集单拥有同等能力。
- 采纳后跟踪待实施、实施中和已完成；暂缓保留待办，不采纳结束处理。
- 正式回复立即对填报者可见，内部备注及草稿不向填报者返回。
- 公示快照由全局管理员或该收集单的单据管理员审核发布；私有进度更新不自动改写已发布内容。选择“不公示”会记录状态并移出待办，之后可重新发布。
- 待我处理的单据管理员范围只包含未办结且未公示、未跳过的需求；批量操作由前端逐条调用单条接口，按每条需求自己的版本校验，部分失败不回滚并汇总提示。

## 二、运行准备

1. 在测试数据库按官方流程建立原社区版表结构；升级现有实例前先备份，不重新导入会删除旧表的官方初始化脚本。
2. 新环境首次执行 `doc/ruima-demand-schema.sql` 一次，仅新增 `rm_demand_*` 表。已有实例先备份，执行 `doc/migration-20261114-form-manager.sql` 一次后再部署新后端与前端；迁移新增 `can_manage`、`publication_skipped` 并为收集单创建人回填单据管理员，不可重复执行。脚本中的独立索引不是重复迁移入口。
3. 复制 `tduck-api/src/main/resources/application-demand.example.yml` 到本机忽略文件，例如 `application-demand.local.yml`，以外部配置方式加载。
4. 按既有运行方式配置数据库、上传存储及原系统参数（当前社区版本使用 EHCache，本测试实例没有新增 Redis）；示例配置只补充需求模块和统一登录参数。
5. 启用 `ruima.demand.enabled` 后，原维护管理员可进入后台；额外管理员可通过配置或管理页面明确授权。
6. 为本系统注册独立登录应用，禁止复用其他业务的客户端密钥。将密钥放在环境变量或本机忽略配置，不进入 Git、日志或文档。

```powershell
mvn -B -pl tduck-api -am test
mvn -B -pl tduck-api -am package
java -jar tduck-api/target/tduck-api.jar --spring.config.additional-location=file:./application-demand.local.yml
```

前端生产包可按原项目部署方式放入后端静态目录或由反向代理提供。同一入口需要分别转发业务接口与前端页面，并支持前端 History 路由回退；`/demand-api/*` 为接口，`/demand/*` 为前端页面，分别转发，避免直接刷新页面时收到 JSON。

## 三、独立登录应用

- 建议应用名：`app-ruima-survey`，显示名：瑞玛需求征集，组织：`ruima`。
- 采用授权码流程，启用 PKCE S256；关闭本应用自助注册，复用现有员工身份及登录方式。
- 本地回调示例：`http://localhost:8999/auth/oidc/callback`。测试服务器回调按实际统一入口配置，例如 `http://192.168.1.240:18000/auth/oidc/callback`。
- 回调地址采用精确白名单；手机访问时不得使用手机自身的 localhost 作为回调。
- 已只读核对现有签发地址为 `http://192.168.1.237:13004`，组织为 `ruima`。浏览器入口与签发地址可以分别配置，不能仅为公网入口而替换令牌 issuer。
- 校验签名、issuer、受众、有效期、nonce、组织及禁用标记。身份按 issuer 与 subject 映射，不通过姓名或邮箱自动合并账户，也不采信身份声明授予本地管理员权限。
- 登录回调只在地址片段中携带短时一次性票据，票据与 HttpOnly 浏览器 Cookie 绑定；原系统会话令牌不进入跳转地址。

## 四、接口与数据

- `/demand-api/capabilities`：模块开关、菜单能力与计数，含 `manage`。
- `/demand-api/forms`、`/demand-api/forms/{key}`：可见收集单与填报方式。
- `/demand-api/forms/{key}/handlers`：单据管理员读取可分派的经办人，仅返回姓名与标识。
- `/demand-api/requests`：本人、待办和获授权总表；支持提交日期范围筛选，返回最近正式回复时间、公示状态及当前账户的 `canHandle`、`canManage`。
- `/demand-api/requests/summary`：按收集单汇总当前范围的条数、未读与待办，口径与列表一致，并返回 `canManage`。
- `/demand-api/export/requests`、`/demand-api/export/publications`：按当前筛选条件导出 `.xlsx`，权限与列表一致，单次最多 10000 行；截断时响应头为 `X-Export-Truncated: true`。
- `/demand-api/requests/{id}/publication`：审核发布或撤回；同级 `/publication/auto` 自动生成并发布，`/publication/skip` 记录不公示。
- `/demand-api/lookup`：匿名查询，凭证放请求体并限速。
- `/demand-api/publications`：仅返回已审核的公示快照，并带所属收集单标识与名称、填报者、经办人及提报时间。
- `/demand-api/admin/*`：配置、具名权限（含 `canManage`）及额外管理员授权。
- `/auth/oidc/*`：登录起始、回调及一次性票据兑换。

原提交记录为需求正文唯一正本。处理索引、消息、已读版本、公示及身份映射放在新增表中。原提交接口与需求索引写入处于同一事务；处理结果和分派使用版本校验及行锁防止覆盖。需求索引新增 `publication_skipped` 记录不公示状态；私有附件通过需求授权下载接口读取，本地 `/u/<收集单摘要>/...` 静态路径拒绝绕过。

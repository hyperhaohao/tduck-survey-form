# 瑞玛需求钉钉推送方案

本文规划把现有站内消息按事件推送到员工钉钉。**结论：使用钉钉企业内部应用工作通知，1:1 推送；首批只推待审批、审批结果、待填报提醒、正式回复、处理结果；钉钉是站内消息之外的提醒渠道，失败不影响业务；当前只完成方案与只读核对，尚未开始钉钉代码。**

## 一、目标与边界

- 站内消息仍是唯一事实来源；钉钉用于提醒，失败不阻断业务事务，也不删除站内消息。
- 使用企业内部应用工作通知，按员工 `userid` 1:1 发送；不使用 `dept_id_list` 或 `to_all_user`，避免误发全员。
- 首批核心事件：`APPROVAL`、`APPROVAL_RESULT`、`REQUIRED`、`REPLY`、`RESULT`。
- 后续可开启：`ASSIGN`、`FOLLOWUP`、`NEW_DEMAND`、`PUBLICATION`；公示建议改每日摘要或群机器人，不默认 1:1。
- 本期不做群机器人、钉钉待办、钉钉内审批、钉钉扫码登录、双向回执。
- 工作通知官方定位是通知类，不是任务对象；审批任务后续可增加钉钉待办通道，本期按用户选择先用工作通知。

## 二、当前事实

- 站内消息由 `backend/tduck-api/.../DemandNotices.java` 统一写入 `rm_demand_notice`，已有 9 种 kind、已读、去重和清理。
- 现有通知方法大多用 `catch (Exception)` 吞异常；`DemandReminderJob` 没有事务；钉钉 outbox 必须先处理事务边界。
- 237 在职本地账户 104 个：邮箱 101 个、手机号 0 个（2026-11-25 只读核对）；只能以邮箱精确匹配为主，其余人工绑定。
- 237 已能访问 `https://oapi.dingtalk.com` 与 `https://api.dingtalk.com`（HTTP 200，2026-11-25 只读检查）。
- 企业内部应用已存在；appKey/appSecret/agentId 稍后放入 237 受限 secrets，不进入 Git、数据库、聊天或日志。
- 后端没有钉钉 SDK、钉钉用户映射或推送表；`tduck-webhook` 是通用表单 Webhook，不复用。

## 三、事件与接收人

| 事件 | 接收人 | 默认 | 说明 |
| --- | --- | --- | --- |
| APPROVAL | 当前级全部候选人 | 开 | 高优先级，立即推送 |
| APPROVAL_RESULT | 填报人 | 开 | 最终通过或任一级驳回 |
| REQUIRED | 必填未提交人 | 开 | 按现有提醒任务；同人同日去重 |
| REPLY | 填报人 | 开 | 正式回复 |
| RESULT | 填报人 | 开 | 处理结果/进度 |
| ASSIGN | 新经办人 | 关 | 可后续开启 |
| FOLLOWUP | 经办人/单据管理员 | 关 | 可后续开启 |
| NEW_DEMAND | 单据管理员 | 关 | 建议摘要 |
| PUBLICATION | 可见范围 | 关 | 建议摘要或群提醒 |

- 标题格式：`【瑞玛问卷】<事件>：<需求标题>`；正文包含收集单、填报人/部门、时间、简短说明。
- 链接：`APPROVAL → /demand/approvals?id=`；`APPROVAL_RESULT/REPLY/RESULT → /demand/mine?id=`；`REQUIRED → /demand/home`；`ASSIGN/FOLLOWUP/NEW_DEMAND → /demand/pending?id=`；`PUBLICATION → /demand/publications?id=`。
- 链接带 `notice=<noticeId>`；目标页打开时标记该条已读，避免从钉钉进入后站内仍显示未读。
- 正文不包含内部备注、查询码、附件或完整答卷；详情以站内为准。

## 四、总体架构

```text
业务事务
  → 写 rm_demand_notice（站内）
  → 发布 DemandNoticeCreatedEvent
提交
  → @TransactionalEventListener(AFTER_COMMIT) 写 rm_demand_push（短事务）
  → 定时派发器抢占到期行
  → 取钉钉 access token（缓存）
  → 工作通知 asyncsend_v2（按 batch_key 合并 userId）
  → SENT / FAILED / SKIPPED / CANCELLED
```

- 业务回滚不会产生 outbox；站内消息写入失败也不会产生推送。
- outbox 写失败只记录日志，站内消息保留；派发前校验通知、需求、收集单仍存在。
- HTTP 调用不在业务线程和长事务中；派发失败按退避重试，不阻塞 09:05 的必填提醒。
- 站内消息与 outbox 不是严格原子；这是为保证业务不被通知阻塞的取舍，后台保留失败/跳过记录。

## 五、数据模型

```sql
CREATE TABLE IF NOT EXISTS rm_demand_dingtalk_user (
  dingtalk_user_id VARCHAR(64) NOT NULL PRIMARY KEY,
  user_id BIGINT NULL,
  name VARCHAR(100) NULL,
  mobile VARCHAR(32) NULL,
  email VARCHAR(200) NULL,
  dept_names VARCHAR(500) NULL,
  active BOOLEAN NOT NULL DEFAULT TRUE,
  status VARCHAR(20) NOT NULL DEFAULT 'UNMATCHED',
  match_source VARCHAR(16) NULL,
  confirmed_by BIGINT NULL,
  confirmed_at TIMESTAMP NULL,
  synced_at TIMESTAMP NULL,
  create_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (user_id)
);

CREATE TABLE IF NOT EXISTS rm_demand_push (
  id VARCHAR(36) NOT NULL PRIMARY KEY,
  notice_id VARCHAR(36) NOT NULL,
  user_id BIGINT NOT NULL,
  dingtalk_user_id VARCHAR(64) NULL,
  kind VARCHAR(24) NOT NULL,
  form_key VARCHAR(64) NULL,
  demand_id VARCHAR(36) NULL,
  publication_id VARCHAR(36) NULL,
  round_no INT NULL,
  step_no INT NULL,
  title VARCHAR(200) NOT NULL,
  content VARCHAR(1000) NULL,
  link_url VARCHAR(512) NULL,
  dedupe_key VARCHAR(64) NOT NULL,
  batch_key VARCHAR(64) NULL,
  status VARCHAR(16) NOT NULL DEFAULT 'PENDING',
  attempts INT NOT NULL DEFAULT 0,
  next_retry_at TIMESTAMP NULL,
  lease_until TIMESTAMP NULL,
  last_error VARCHAR(500) NULL,
  provider_task_id VARCHAR(64) NULL,
  sent_at TIMESTAMP NULL,
  create_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (dedupe_key)
);
CREATE INDEX idx_push_due ON rm_demand_push(status, next_retry_at);
CREATE INDEX idx_push_lease ON rm_demand_push(status, lease_until);
CREATE INDEX idx_push_batch ON rm_demand_push(batch_key, status);
CREATE INDEX idx_push_notice ON rm_demand_push(notice_id);
CREATE INDEX idx_push_user ON rm_demand_push(user_id, create_time);

CREATE TABLE IF NOT EXISTS rm_demand_push_setting (
  setting_key VARCHAR(64) NOT NULL PRIMARY KEY,
  setting_value VARCHAR(500) NOT NULL,
  updated_by BIGINT NULL,
  update_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

- `dedupe_key = SHA-256(noticeId + kind + title + content)`；公示重新发布若内容变化，允许新推送；内容不变则幂等忽略。
- `batch_key` 由事件、收集单、需求/公示、轮次、步骤、标题、正文和链接生成；同一内容的多条 outbox 合并为一次工作通知，`userid_list` 最多 100 人。
- 状态：`PENDING/SENDING/SENT/FAILED/DEAD/SKIPPED/CANCELLED`；`SKIPPED` 保存 `NO_MAPPING/USER_INACTIVE/USER_OPT_OUT` 等原因。
- 迁移文件名建议 `doc/ruima-demand-migration-20261127-dingtalk-push.sql`；同样 DDL 同步到 `doc/ruima-demand-schema.sql`，H2 测试自动加载。

## 六、后端设计

- 新增 `DemandDingTalkProperties`：`ruima.demand.dingtalk.*` 配置。
- 新增 `DemandDingTalkClient`：token 缓存、`asyncsend_v2`、部门/成员 HTTP；使用 `RestTemplate`，不新增 Maven 依赖。
- 新增 `DemandDingTalkDirectory`：通讯录同步、精确匹配、绑定/解绑、映射查询。
- 新增 `DemandPushSettings`：读写 `rm_demand_push_setting`，30 秒内存快照；管理员保存后失效。
- 新增 `DemandPush`：outbox 入队、派发、重试、清理、链接、删除；依赖 store/settings/client/properties，不依赖 `DemandNotices`。
- 新增 `DemandDingTalkController`：状态、设置、测试连接、同步、映射、测试发送、推送日志和重试；仅全局管理员。
- `DemandNotices` 在 `insert/insertWithStep` 生成 notice id 后发布事件；`publication` 的 UPDATE 和 batch INSERT 两条路径分别发布；`DemandNotices` 构造器新增 `ApplicationEventPublisher`。
- `DemandReminderJob.requiredReminder` 补 `@Transactional`；`DemandPush` 的 after-commit 监听器用 `REQUIRES_NEW` 写 outbox，异常只记录。
- 删除需求/公示/收集单时同步删除或取消 push 行；`SENT` 保留 30 天、`SKIPPED/DEAD/FAILED` 保留 90 天清理。
- 派发前检查 `rm_demand_notice.read_at`、`ac_user.deleted`、映射状态和对象存在；或签完成后取消同一步骤其他候选人的待推送。
- 调度使用 `@Scheduled(fixedDelayString=...)`；建议 `spring.task.scheduling.pool.size: 3`，避免派发 HTTP 阻塞提醒任务。

## 七、身份映射

- 同步流程：根部门 `dept_id=1` 起 BFS 部门树，`topapi/v2/user/list` 分页拉成员，保存 `userid/name/mobile/email/dept_names/active`。
- 自动匹配只用邮箱精确匹配（小写、去空格）；237 邮箱 101/104、手机号 0，不能依赖手机号。
- 映射状态：`PENDING_CONFIRM`（精确命中待确认）、`CONFIRMED`（参与推送）、`UNMATCHED`（无本地匹配）、`CONFLICT`（命中多个/已被占用）、`INVALID`（离职/停用）。
- 管理员在后台逐条确认或“批量确认精确匹配”；未匹配项手工绑定；可提供 `dingtalkUserId,localUserId` CSV 导入，均记录 `confirmed_by/at`。
- 禁止按姓名自动绑定；派发时重新校验映射仍为 `CONFIRMED`，防止把旧消息发给新绑定人。
- 应用需要通讯录部门/成员读权限；手机号、邮箱字段还需对应字段权限；可见范围必须覆盖员工。

## 八、配置与安全

```yaml
ruima:
  demand:
    dingtalk:
      enabled: false
      app-key: ${DINGTALK_APP_KEY:}
      app-secret: ${DINGTALK_APP_SECRET:}
      agent-id: ${DINGTALK_AGENT_ID:0}
      api-base: https://oapi.dingtalk.com
      link-base: ${DINGTALK_LINK_BASE:}
      dispatch-delay-ms: 30000
      dispatch-batch-size: 50
      max-attempts: 5
      lease-seconds: 120
      monthly-call-limit: 9000
```

- 真实值只放 `/data/apps/ruima-survey/secrets/application-test.yml`（root 0600，容器只读挂载），不进入 Git、数据库、聊天、日志或截图。
- 两层开关：部署总开关 `ruima.demand.dingtalk.enabled` + 数据库 `rm_demand_push_setting.enabled`；两者都开且凭证/link base 完整才生效。
- 事件开关、安静时段、`link.base` 存 `rm_demand_push_setting`；默认安静时段 20:00–08:00，`APPROVAL` 默认绕过（可配置）。
- 日志只记录 push id、kind、user id、状态、`request_id/task_id`、错误码；不记录 token、appSecret、完整正文、手机号。
- 测试发送默认只发给当前管理员本人；禁止在验收中使用 `to_all_user` 或生产全员。

## 九、前端设计

- 后台管理新增全局管理员可见「钉钉推送」页签；组件独立为 `components/DingTalkPanel.vue`，不继续膨胀 `Admin.vue`。

- 用户管理页后续显示「钉钉已绑定/待确认/未绑定」标签；绑定/解绑仅全局管理员或获授权用户管理员。
- 消息中心后续增加「接收钉钉提醒」用户开关；管理员总开关和事件开关优先级更高。
- 推送链接带 `notice=<noticeId>`；消息中心、我的需求、待我审批、需求公示打开时标记该条已读。
- 1024/390 布局：表格外层横向滚动，栅格在窄屏转单列，按钮全宽；复用现有 `.demand-*` 视觉类。

## 十、钉钉接口与限制

| 项目 | 值/说明 |
| --- | --- |
| Token | 经典 `GET https://oapi.dingtalk.com/gettoken`，约 7200 秒，缓存并提前 5 分钟刷新 |
| 工作通知 | `POST .../topapi/message/corpconversation/asyncsend_v2`，`agent_id`、`userid_list`、`msg` |
| 消息体 | 推荐 `action_card`（标题、markdown、单个「查看详情」按钮）；`msg` 最长 2048 字节 |
| 接收人 | 只用 `userid_list`，单次最多 100 人；禁止部门/全员群发 |
| 频率 | 5000 接收人/分钟/应用；500 条/天/用户；同内容 1 条/天/用户 |
| 配额 | 标准版组织所有内部应用约 10000 次/月；逐条发送会耗尽，必须按 `batch_key` 合并 |
| 结果 | `errcode=0` 仅表示受理；可查 `task_id` 结果（24 小时内、接收人不超过 100） |
| 通讯录 | `topapi/v2/department/listsub` + `topapi/v2/user/list`；字段权限决定手机/邮箱是否返回 |
| 常用错误 | `60011` 权限/可见范围；`143105` 当日上限；`143106` 内容重复；`90018` QPS；`40014/42001` token 过期 |
| Token 代际 | 经典 token 配 `oapi` 经典接口；新版 token 配 `api.dingtalk.com` 头；不混用 |

- `errcode=0` 不代表送达；第一期以 `SENT` 表示“已提交钉钉”，不逐条查送达，避免配额消耗；重要事件后续可加结果查询。
- 工作通知不是任务对象；审批任务后续可加钉钉待办（`Todo.Todo.Write`），本期不实现。
- 官方文档：发送工作通知、消息类型、token、频率限制、发送结果、通讯录部门/成员、全局错误码（见第十四节）。

## 十一、分阶段实施

1. 只读核对（部分完成）：邮箱/手机号/出口已核对；待核对应用可见范围、工作通知权限、通讯录字段权限、IP 白名单、组织版本和月度配额、外网链接基址。
2. 导航调整（已完成独立部分）：消息中心移到首页下方，静态部署 237；与钉钉无关。
3. 钉钉代码骨架（默认关闭）：迁移、配置、client、directory、push、settings、管理接口、`DingTalkPanel.vue`、H2/mock 测试；部署 237 但不外呼。
4. 映射与测试发送：secrets 就绪，同步通讯录，确认管理员映射，测试连接和测试发送只到管理员本人。
5. 核心事件开启：先开 APPROVAL 验证，再开 APPROVAL_RESULT/REPLY/RESULT/REQUIRED；逐事件观察。
6. 后续：ASSIGN/FOLLOWUP/NEW_DEMAND/PUBLICATION、用户偏好、每日摘要、群机器人、钉钉待办、多实例 token 锁。

## 十二、验证与验收

- 后端 H2：事件开关、无映射、已读跳过、或签取消、dedupe/batch、token 过期、429/5xx 退避、租约回收、删除清理、2048 字节截断、月度配额停止。
- HTTP 使用可注入 transport + FakeDingTalkTransport；CI 不访问真实钉钉，`enabled=false`。
- 前端：页签权限、设置保存、同步统计、映射筛选/绑定、测试发送二次确认、1024/390 无溢出；现有回归通过。
- 真实环境只向管理员本人钉钉发送测试；用合成审批需求验证 APPROVAL 和 APPROVAL_RESULT；不向全体员工发送。
- 验收后按精确 ID 清理合成需求、答卷、消息、push、部门、用户；记录清理前后计数。

## 十三、风险与待确认

- **配额**：标准版约 10000 次/月；必须按 `batch_key` 合并，逐条发送不可行；上线前确认组织版本。
- **身份数据**：邮箱 101/104、手机号 0；自动匹配可能不完整，需人工绑定或 HR 对照表；不按姓名匹配。
- **应用权限**：可见范围、工作通知、通讯录/字段权限、IP 白名单任一不满足会导致同步为空或 `60011`。
- **工作通知定位**：不是任务对象；审批任务后续可加钉钉待办。
- **链接登录**：钉钉内打开先跳 Casdoor 登录；需真实验收；HTTP 明文可能受客户端策略限制，建议 HTTPS。
- **事务边界**：现有通知吞异常、提醒无事务；实现前先补事务和 after-commit 事件，避免 rollback-only 或半成功。
- **PII**：outbox/映射表保存标题、正文、邮箱；需 30/90 天清理和业务删除级联。
- **调度池**：默认单线程；派发 HTTP 需独立池，避免延迟提醒任务。
- **待确认**：应用权限/可见范围、组织版本/配额、外网 HTTPS 基址、映射确认权限（只全局管理员还是含 `org`）、安静时段和审批绕过默认值。

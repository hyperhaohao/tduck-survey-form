# 瑞玛需求钉钉推送方案

本文规划把现有站内消息按事件推送到员工钉钉，包含工作通知和钉钉待办。**结论：审批任务和待填报提醒创建钉钉待办，同时发工作通知；审批结果、正式回复、处理结果只发工作通知；钉钉是站内消息之外的提醒渠道，失败不影响业务。代码已完成并部署 240，240 的应用凭证尚未配置；先完成 240 真实钉钉测试，通过后再迁移 237。**

## 一、目标与边界

- 站内消息仍是唯一事实来源；钉钉用于提醒和任务，失败不阻断业务事务，也不删除站内消息。
- 审批任务：为当前级每个审批人创建钉钉待办，同时发工作通知；任一人通过/驳回后，完成该级全部待办；下一级再创建。
- 待填报提醒：为未提交的必填人创建钉钉待办，同时发工作通知；该用户提交后完成待办。
- 审批结果、正式回复、处理结果：只发工作通知，不建待办。
- 后续可开启：`ASSIGN`、`FOLLOWUP`、`NEW_DEMAND`、`PUBLICATION` 的工作通知；待办不扩展到这些事件。
- 本期不做群机器人、钉钉内审批、钉钉扫码登录、双向回执。
- 先在 240 完成真实钉钉测试，通过后再迁移 237；240 已于 2026-11-26 升级到当前版本。

## 三、事件与接收人

| 事件 | 接收人 | 钉钉待办 | 工作通知 |
| --- | --- | --- | --- |
| APPROVAL | 当前级全部候选人 | 开 | 开 |
| REQUIRED | 必填未提交人 | 开 | 开 |
| APPROVAL_RESULT | 填报人 | 关 | 开 |
| REPLY | 填报人 | 关 | 开 |
| RESULT | 填报人 | 关 | 开 |
| ASSIGN | 新经办人 | 关 | 关（可开） |
| FOLLOWUP | 经办人/管理员 | 关 | 关（可开） |
| NEW_DEMAND | 单据管理员 | 关 | 关（可开） |
| PUBLICATION | 可见范围 | 关 | 关（可开） |

- 待办 `subject`：`【瑞玛问卷】待审批：<需求标题>` 或 `【瑞玛问卷】待填报：<收集单名称>`。
- 待办 `description`：收集单、填报人/部门、当前级、截止时间；不写内部备注、查询码、附件或完整答卷。
- 待办 `sourceId`：审批 `APPROVAL:<demandId>:<stepNo>:<userId>`；待填报 `REQUIRED:<formKey>:<roundNo>:<userId>`，用于钉钉侧幂等。
- 链接：`APPROVAL → /demand/approvals?id=`；`APPROVAL_RESULT/REPLY/RESULT → /demand/mine?id=`；`REQUIRED → /demand/home`；`ASSIGN/FOLLOWUP/NEW_DEMAND → /demand/pending?id=`；`PUBLICATION → /demand/publications?id=`。
- 待办创建时设置 `notifyConfigs.dingNotify=false`、`sendTodoApn=false`、`sendAssistantChat=false`，由工作通知承担即时提醒，避免同一事件两次钉钉通知；待办仍出现在「待我处理」。
- 审批人或签：任一人动作后完成该级全部待办，其他审批人的钉钉任务消失；工作通知保留为历史提醒。

## 四、总体架构

```text
业务事务
  → 写 rm_demand_notice（站内）
  → 发布 DemandNoticeCreatedEvent
提交
  → AFTER_COMMIT 监听器写 rm_demand_push（短事务）
      APPROVAL/REQUIRED → TODO CREATE + WORK CREATE
      其他核心事件       → WORK CREATE
  → 定时派发器抢占到期行
      WORK: 经典 token + asyncsend_v2（按 batch_key 合并 userId）
      TODO: 新版 token + v1.0/todo 创建/完成/删除
  → SENT / FAILED / SKIPPED / CANCELLED
```

- 业务回滚不会产生 outbox；站内消息写入失败也不会产生推送。
- outbox 写失败只记录日志，站内消息保留；派发前校验通知、需求、收集单仍存在。
- 审批步骤完成、填报提交、需求删除时，另写 TODO COMPLETE/DELETE 动作；派发器调用钉钉待办状态接口。
- HTTP 调用不在业务线程和长事务中；派发失败按退避重试，不阻塞 09:05 的必填提醒。
- 站内消息与 outbox 不是严格原子；这是为保证业务不被通知阻塞的取舍，后台保留失败/跳过记录。

## 五、数据模型

```sql
CREATE TABLE IF NOT EXISTS rm_demand_dingtalk_user (
  dingtalk_user_id VARCHAR(64) NOT NULL PRIMARY KEY,
  union_id VARCHAR(64) NULL,
  user_id BIGINT NULL,
  name VARCHAR(100) NULL,
  mobile VARCHAR(32) NULL,
  email VARCHAR(200) NULL,
  dept_names VARCHAR(500) NULL,
  active BOOLEAN NOT NULL DEFAULT TRUE,
  status VARCHAR(20) NOT NULL DEFAULT 'UNMATCHED',
  match_source VARCHAR(16) NULL,
  confirmed_by BIGINT NULL,
  confirmed_at TIMESTAMP NULL,
  synced_at TIMESTAMP NULL,
  create_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (user_id)
);
CREATE INDEX idx_ding_user_status ON rm_demand_dingtalk_user(status, active);
CREATE INDEX idx_ding_user_union ON rm_demand_dingtalk_user(union_id);

CREATE TABLE IF NOT EXISTS rm_demand_push (
  id VARCHAR(36) NOT NULL PRIMARY KEY,
  notice_id VARCHAR(36) NULL,
  user_id BIGINT NOT NULL,
  dingtalk_user_id VARCHAR(64) NULL,
  union_id VARCHAR(64) NULL,
  channel VARCHAR(16) NOT NULL,
  action VARCHAR(16) NOT NULL,
  kind VARCHAR(24) NOT NULL,
  form_key VARCHAR(64) NULL,
  demand_id VARCHAR(36) NULL,
  publication_id VARCHAR(36) NULL,
  round_no INT NULL,
  step_no INT NULL,
  parent_id VARCHAR(36) NULL,
  source_id VARCHAR(128) NULL,
  todo_task_id VARCHAR(64) NULL,
  provider_task_id VARCHAR(64) NULL,
  title VARCHAR(200) NOT NULL,
  content VARCHAR(1000) NULL,
  link_url VARCHAR(512) NULL,
  dedupe_key VARCHAR(64) NOT NULL,
  batch_key VARCHAR(64) NULL,
  status VARCHAR(16) NOT NULL DEFAULT 'PENDING',
  attempts INT NOT NULL DEFAULT 0,
  next_retry_at TIMESTAMP NULL,
  lease_until TIMESTAMP NULL,
  locked_by VARCHAR(64) NULL,
  last_error VARCHAR(500) NULL,
  sent_at TIMESTAMP NULL,
  create_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (dedupe_key)
);
CREATE INDEX idx_push_due ON rm_demand_push(status, next_retry_at);
CREATE INDEX idx_push_lease ON rm_demand_push(status, lease_until);
CREATE INDEX idx_push_batch ON rm_demand_push(batch_key, status);
CREATE INDEX idx_push_notice ON rm_demand_push(notice_id);
CREATE INDEX idx_push_user ON rm_demand_push(user_id, create_time);
CREATE INDEX idx_push_parent ON rm_demand_push(parent_id);
CREATE INDEX idx_push_source ON rm_demand_push(source_id);

CREATE TABLE IF NOT EXISTS rm_demand_push_setting (
  setting_key VARCHAR(64) NOT NULL PRIMARY KEY,
  setting_value VARCHAR(500) NOT NULL,
  updated_by BIGINT NULL,
  update_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

- `channel`：`WORK` 工作通知、`TODO` 钉钉待办；`action`：`CREATE/COMPLETE/DELETE`。
- `parent_id`：COMPLETE/DELETE 指向原 TODO CREATE 行；原行保存 `todo_task_id`、`source_id`。
- `dedupe_key`：WORK 按 `noticeId + kind`；TODO CREATE 按 `sourceId`；TODO COMPLETE/DELETE 按 `parent_id + action`。
- `batch_key`：工作通知同内容合并；`userid_list` 最多 100 人，钉钉待办按人创建。
- 状态：`PENDING/SENDING/SENT/FAILED/DEAD/SKIPPED/CANCELLED/DONE`；`SKIPPED` 保存 `NO_MAPPING/NO_CREATOR/USER_INACTIVE/USER_OPT_OUT` 等原因。
- 迁移文件名建议 `doc/ruima-demand-migration-20261127-dingtalk-push.sql`；同样 DDL 同步到 `doc/ruima-demand-schema.sql`。

## 六、后端设计

- 新增 `DemandDingTalkProperties`：`ruima.demand.dingtalk.*` 配置，含 appKey/appSecret/agentId、creatorUserId/creatorUnionId、linkBase、dispatch、重试、配额。
- 新增 `DemandDingTalkClient`：经典 token 与新版 token 分开缓存；工作通知、通讯录、待办创建/状态/删除；使用 `RestTemplate`，不新增 Maven 依赖。
- 新增 `DemandDingTalkDirectory`：通讯录同步、邮箱匹配、绑定/解绑、`unionId` 解析、TODO 创建者解析。
- 新增 `DemandPushSettings`：读写 `rm_demand_push_setting`，30 秒内存快照；管理员保存后失效。
- 新增 `DemandPush`：事件监听、outbox、派发、重试、清理、链接、删除；依赖 store/settings/client/properties，不依赖 `DemandNotices`。
- 新增 `DemandDingTalkController`：状态、设置、测试连接、同步、映射、测试发送、推送日志和重试；仅全局管理员。
- `DemandNotices` 在 `insert/insertWithStep` 生成 notice id 后发布事件；`publication` 的 UPDATE 和 batch INSERT 两条路径分别发布；构造器新增 `ApplicationEventPublisher`。
- `DemandApproval.decide` 在步骤更新后调用 `DemandPush.completeApprovalStep(demandId, stepNo)`，为原 TODO 行写 COMPLETE 动作；或签全部完成。
- `DemandSubmission.after` 在提交成功后调用 `DemandPush.completeRequired(userId, formKey, roundNo)`，完成该用户本轮待填报待办。
- `DemandWorkflow.deleteDemand`、`DemandForms.deleteCollection` 删除/取消对应 TODO；避免已删除需求的待办残留。
- `DemandReminderJob.requiredReminder` 补 `@Transactional`；`DemandPush` 的 after-commit 监听器用 `REQUIRES_NEW` 写 outbox，异常只记录。
- 派发前检查 `ac_user.deleted`、映射 `CONFIRMED`、`UNION_ID` 存在、对象存在；WORK 已读可跳过，TODO 不因站内已读跳过（已读不等于已处理）。
- 调度使用 `@Scheduled(fixedDelayString=...)`；建议 `spring.task.scheduling.pool.size: 3`。

## 七、身份映射

- 同步流程：根部门 `dept_id=1` 起 BFS 部门树，`topapi/v2/user/list` 分页拉成员，保存 `userid/unionid/name/mobile/email/dept_names/active`。
- 自动匹配只用邮箱精确匹配（小写、去空格）；237 邮箱 101/104、手机号 0，不能依赖手机号。
- 映射状态：`PENDING_CONFIRM`（精确命中待确认）、`CONFIRMED`（参与推送）、`UNMATCHED`（无本地匹配）、`CONFLICT`（命中多个/已被占用）、`INVALID`（离职/停用）。
- 管理员在后台逐条确认或“批量确认精确匹配”；未匹配项手工绑定；可提供 `dingtalkUserId,localUserId` CSV 导入，均记录 `confirmed_by/at`。
- 禁止按姓名自动绑定；派发时重新校验映射仍为 `CONFIRMED`，防止把旧消息发给新绑定人。
- 待办创建者：优先使用配置的 `creatorUnionId`；未配置时用 `creatorUserId` 的已确认映射；两者都没有则 TODO 标记 `NO_CREATOR`，工作通知仍可发。
- 应用需要通讯录部门/成员读权限、工作通知权限、待办写权限；可见范围必须覆盖员工。

## 十、钉钉接口与限制

| 项目 | 值/说明 |
| --- | --- |
| 经典 token | `GET https://oapi.dingtalk.com/gettoken`，约 7200 秒，用于工作通知/通讯录 |
| 新版 token | `POST https://api.dingtalk.com/v1.0/oauth2/accessToken`，用于待办 API，头 `x-acs-dingtalk-access-token` |
| 工作通知 | `POST .../topapi/message/corpconversation/asyncsend_v2`，`agent_id`、`userid_list`、`msg` |
| 待办创建 | `POST https://api.dingtalk.com/v1.0/todo/users/{creatorUnionId}/tasks` |
| 待办完成 | `PUT .../tasks/{taskId}`，body `{"done":true}`；创建者完成会级联完成执行人 |
| 待办删除 | `DELETE .../tasks/{taskId}` |
| 待办权限 | `Todo.Todo.Write`/`todo.write`；路径 `{unionId}` 为创建者，`creatorId` 同创建者，`executorIds` 为审批人 |
| 待办幂等 | `sourceId` 全局唯一；重复创建返回参数错误，需查询或事件补偿 |
| 消息体 | 工作通知 `msg` 最长 2048 字节；正文截断 |
| 接收人 | 工作通知只用 `userid_list`，单次最多 100 人；禁止部门/全员群发 |
| 频率 | 5000 接收人/分钟/应用；500 条/天/用户；同内容 1 条/天/用户 |
| 配额 | 标准版组织所有内部应用约 10000 次/月；工作通知按 `batch_key` 合并，待办按人创建 |
| 常用错误 | `60011` 权限/可见范围；`143105` 当日上限；`143106` 内容重复；`90018` QPS；`40014/42001` token 过期 |

- 工作通知 `errcode=0` 仅表示受理；第一期以 `SENT` 表示“已提交钉钉”，不逐条查送达。
- 待办创建时 `notifyConfigs.dingNotify=false`、`sendTodoApn=false`、`sendAssistantChat=false`，由工作通知提醒；`isOnlyShowExecutor=true`，任务只出现在执行人待办。待办创建者优先使用独立管理员/服务账号，避免创建者与执行人相同导致 DING 被抑制。
- 工作通知不是任务对象；审批/待填报使用待办解决任务跟踪。
- 官方文档：工作通知、消息类型、token、频率限制、发送结果、通讯录、待办创建/状态、全局错误码（见第十四节）。

## 十二、验证与验收

## 十三、风险与待确认

- **待办创建者**：钉钉待办要求创建者 unionId，且创建者与执行人相同时可能不提醒；需要确认一个管理员作为创建者并提供 unionId/映射。
- **应用权限**：可见范围、工作通知、通讯录/字段权限、待办写权限、IP 白名单任一不满足会导致同步为空、待办失败或 `60011`。
- **配额**：标准版约 10000 次/月；工作通知必须合并，待办按人创建；上线前确认组织版本和待办 API 配额。
- **身份数据**：邮箱 101/104、手机号 0；自动匹配可能不完整，需人工绑定或 HR 对照表；不按姓名匹配。
- **240 已升级**：当前已部署到 2026-11-26 构建，缺失迁移已补齐；真实钉钉测试仍需应用凭证和 240 可达链接。
- **链接登录**：钉钉内打开先跳 Casdoor 登录；需真实验收；HTTP 明文可能受客户端策略限制，建议 HTTPS。
- **事务边界**：现有通知吞异常、提醒无事务；实现已用 after-commit 事件 + 独立 outbox 事务，避免 rollback-only 或半成功。
- **PII**：outbox/映射表保存标题、正文、邮箱；需 30/90 天清理和业务删除级联。
- **调度池**：默认单线程；派发 HTTP 需独立池，避免延迟提醒任务。
- **待确认**：待办创建者账号、应用权限/可见范围、组织版本/配额、外网 HTTPS 基址、安静时段和审批绕过默认值。

# 瑞玛需求审批流方案

本文给出填报审批的简化设计，并已于 2026-11-25 按此实现。**结论：审批只增加一级——部门主管审批，按收集单开关，默认关闭。提交后若开启，需求先进入填报人部门主管的「待我审批」；主管通过后再进入现有单据处理流程（单据管理员/经办人），驳回则结束并通知填报人。不再增加单据管理员或全局管理员审批级。**

## 一、目标与范围

- 按收集单配置「是否需要部门主管审批」，默认不需要。
- 审批链只有一级：填报人提交 → 部门主管审批 → 现有单据处理。
- 单据管理员、全局管理员仍是现有处理与兜底的最终角色，不进入审批链，也不新增审批级。
- 审批通过不自动分派经办人；进入现有待办后仍由单据管理员分派、经办、采纳与公示。

## 二、配置

- `rm_demand_form.requires_leader_approval`：布尔，默认 `FALSE`。
- 开启审批时自动关闭匿名填报，因为匿名无法确定填报人部门与审批人。
- 收集配置中显示开关与提示：开启前需在「用户管理」页为相关部门配置主管。
- 只收集收集单也可以开启；通过后进入只收集未读待办，不进入回复/公示。

## 三、状态机

```text
不开启：提交 → approval_status=NONE → 现有经办/管理待办

开启：  提交 → approval_status=PENDING（待部门主管审批）
          ├─ 主管通过 → approval_status=APPROVED → 现有经办/管理待办
          └─ 主管驳回 → approval_status=REJECTED → 结束，通知填报人
```

- `PENDING` 与 `REJECTED` 不进入现有待办；`PENDING` 只进入审批人的「待我审批」。
- 审批通过后才允许分派、采纳、回复、发布公示等处理动作。
- 驳回后需求终止；原表单不支持编辑，暂不支持修改重提。

## 四、审批人

- 按填报人所属部门：`rm_demand_user_dept` → `rm_demand_dept.leader_id`。
- 只取有效主管：部门 `active=TRUE`、主管账户未停用、且不是填报人本人。
- 多部门：按 `sort_no,name` 取第一个有效主管，不做会签，也不做多级审批。
- 本人即主管：尝试下一个有效部门主管；都不可用则跳过审批。
- 无主管可用：跳过审批，直接进入现有单据流程，并在时间线记录「未配置部门主管，已直接进入处理」。
- 审批人不需要额外平台权限；待办按 `approval_leader_id` 判定。

## 五、数据模型

```sql
ALTER TABLE rm_demand_form ADD COLUMN requires_leader_approval BOOLEAN NOT NULL DEFAULT FALSE;

ALTER TABLE rm_demand ADD COLUMN approval_status VARCHAR(16) NOT NULL DEFAULT 'NONE';
ALTER TABLE rm_demand ADD COLUMN approval_leader_id BIGINT NULL;
ALTER TABLE rm_demand ADD COLUMN approval_comment VARCHAR(2000) NULL;
ALTER TABLE rm_demand ADD COLUMN approval_at TIMESTAMP NULL;
```

- 单级审批不新建审批表，审批状态、审批人、意见与时间直接落在需求上。
- 审批记录写需求时间线 `rm_demand_message`：提交待审批、通过、驳回各一条，类型可用 `APPROVAL`。
- 消息中心使用 `APPROVAL`（待审批任务）与 `APPROVAL_RESULT`（审批结果）两种通知；前端分别显示「待审批」「审批结果」。

## 六、接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/demand-api/requests?scope=approval` | 待我审批列表，返回提交人、部门、提交时间与状态 |
| GET | `/demand-api/requests/summary?scope=approval` | 待我审批按收集单汇总 |
| POST | `/demand-api/requests/{id}/approval` | body `{decision:'APPROVE'\|'REJECT', comment, revision}` |
| GET | `/demand-api/requests/{id}` | 增加 `approvalStatus/approvalLeaderName/approvalComment/approvalAt/canApprove` |
| POST | `/demand-api/admin/forms/{key}` | 现有收集配置增加 `requiresLeaderApproval` |
| GET | `/demand-api/capabilities` | 增加 `approvalPending` 角标计数 |

规则：

- 审批接口使用 `revision` 乐观锁与需求行锁；重复审批、已被处理返回 409，非当前审批人返回 403。
- `assign/outcome/reply/followUp/publish/autoPublish/skip` 在处理前校验 `approval_status`：`PENDING` 返回 409「需求待部门主管审批」，`REJECTED` 返回 409「需求审批未通过」。
- 删除需求时审批字段随时间线一并清理。

## 七、页面

- 收集配置：新增「需要部门主管审批」开关；开启时自动关闭匿名，并提示先配置部门主管。
- 侧栏新增「待我审批」入口与 `approvalPending` 角标；列表复用需求列表组件，`scope=approval`，显示提交人、部门、提交时间与状态。
- 详情抽屉：`canApprove` 时显示审批区（意见输入、通过、驳回）；审批中隐藏经办处理区；操作后刷新并派发 `demand-updated`。
- 我的需求：列表与详情显示「待审批/已通过/已驳回」标签及驳回意见。
- 消息中心：新增「待审批」与「审批结果」类型，点击分别跳转待我审批或我的需求。

## 八、通知

- 提交且需审批：通知部门主管（`APPROVAL`），不通知单据管理员。
- 主管通过：通知填报人（`APPROVAL_RESULT`），并通知单据管理员（`NEW_DEMAND`）。
- 主管驳回：通知填报人（`APPROVAL_RESULT`，含驳回意见），不通知单据管理员。
- 无主管跳过审批：直接通知单据管理员 `NEW_DEMAND`，时间线记录跳过原因。
- 钉钉后续按事件类型接入，站内消息仍为唯一事实来源。

## 九、边界与风险

- 匿名：开启审批时强制关闭匿名；存量匿名需求不追溯审批。
- 只收集：可开启审批；通过后进入只收集未读待办。
- 部门主管数据：当前 12 个部门主管均为空，开启前需补齐；缺失时按跳过规则处理并在界面提示。
- 配置变更：只影响新提交；在途需求保留提交时解析的 `approval_leader_id`。
- 并发：审批与处理均使用行锁 + `revision`，后到者 409。
- 删除：需求删除时审批字段与时间线一并删除；收集单逻辑删除保留历史。

## 十、实施阶段

1. 数据与状态机：收集单开关、`rm_demand` 审批字段、时间线消息。
2. 后端：提交时解析主管并启动审批、`scope=approval`、审批接口、处理门禁、`approvalPending` 计数。
3. 前端：收集配置开关、待我审批列表/入口、详情审批区、我的需求状态标签、消息中心两种类型。

5. 钉钉审批（可选后续）：按事件类型接入外部通知或审批卡片，站内状态保持同步。

## 十二、实现默认值

本文第十一节列出的原待确认项，实现时采用以下默认值：

1. 无可用主管：跳过审批，直接进入现有单据流程，时间线记录原因。
2. 多部门：按 `sort_no,name` 取第一个有效主管。
3. 驳回后：需求终止，不进入处理待办，暂不支持修改重提。
4. 审批通过：不自动分派经办人，仍由单据管理员处理。

# 瑞玛需求审批流方案

本文给出填报审批的多级设计，并已于 2026-11-25 实现。**结论：收集单审批默认「不审批」，可选「直属主管审批」或「逐级审批」；部门主管支持多选，同级或签；逐级审批从填报人部门逐级向上到所有上级，无主管的部门跳过；整条链无主管时直接进入现有处理流程。审批链在提交时固化，聚合状态保持待审批到最后一层通过。**

## 一、目标与规则

- 按收集单配置审批方式：`NONE`（默认，不审批）、`DIRECT`（直属主管）、`HIERARCHY`（逐级审批）。
- 直属主管：只取填报人所属部门的有效主管；部门无主管则不启动审批。
- 逐级审批：从填报人所属部门开始，沿部门上级逐级到根部门；每级有有效主管才生成审批步骤，无主管的部门跳过。
- 同一级多名主管为**或签**：任一人通过即该级通过，其他候选人的待办和消息即时失效；后到操作返回 409。
- 审批链在提交时固化：部门名称、每级候选人写入步骤表；后续部门或主管调整不影响在途需求。
- 聚合状态 `PENDING` 保持到最后一层通过；中间层通过不通知单据管理员、不进入普通待办。
- 任一级驳回即终止；后续未开始步骤标记 `SKIPPED`，通知填报人，不通知单据管理员。
- 最终通过后进入现有单据处理流程；审批通过不自动分派经办人，仍由单据管理员/经办人处理。
- 开启审批时强制关闭匿名；匿名提交无法确定部门与审批人。

## 二、数据模型

新增迁移 `doc/ruima-demand-migration-20261126-multi-leader-approval.sql`，并同步 `doc/ruima-demand-schema.sql`。

```sql
CREATE TABLE rm_demand_dept_leader (
  dept_key VARCHAR(64) NOT NULL,
  user_id BIGINT NOT NULL,
  sort_no INT NOT NULL DEFAULT 0,
  created_by BIGINT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY(dept_key, user_id)
);

ALTER TABLE rm_demand_form ADD COLUMN approval_mode VARCHAR(16) NOT NULL DEFAULT 'NONE';
ALTER TABLE rm_demand ADD COLUMN approval_mode VARCHAR(16) NOT NULL DEFAULT 'NONE';
ALTER TABLE rm_demand ADD COLUMN approval_step INT NOT NULL DEFAULT 0;
ALTER TABLE rm_demand_notice ADD COLUMN step_no INT NULL;
```

- `rm_demand_dept.leader_id` 保留为「第一主管」兼容列；多主管写入时同步写排序第一个，读接口同时返回 `leaderId/leaderName` 与 `leaderIds/leaders`。
- `rm_demand_form.approval_mode` 为主配置；`requires_leader_approval` 保留双写，旧前端或旧后端回滚可用。
- `rm_demand.approval_mode` 是提交时的模式快照；`approval_step` 为当前级号，`NONE` 为 0。
- `rm_demand.approval_status` 聚合状态：`NONE/PENDING/APPROVED/REJECTED`。
- `rm_demand.approval_leader_id/comment/at` 保留为「最近一次审批动作」兼容字段；多级以步骤表为准。

```sql
CREATE TABLE rm_demand_approval_step (
  id VARCHAR(36) PRIMARY KEY,
  demand_id VARCHAR(36) NOT NULL,
  step_no INT NOT NULL,
  dept_key VARCHAR(64) NULL,
  dept_name VARCHAR(512) NULL,
  status VARCHAR(16) NOT NULL DEFAULT 'WAITING',
  comment_text VARCHAR(2000) NULL,
  acted_by BIGINT NULL,
  acted_at TIMESTAMP NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(demand_id, step_no)
);

CREATE TABLE rm_demand_approval_approver (
  step_id VARCHAR(36) NOT NULL,
  user_id BIGINT NOT NULL,
  user_name VARCHAR(100) NOT NULL,
  PRIMARY KEY(step_id, user_id)
);
```

- 步骤状态：`WAITING`（等待前级）、`PENDING`（当前）、`APPROVED`、`REJECTED`、`SKIPPED`（前级驳回后终止）。
- 每步保存部门键、完整部门路径快照、候选人姓名快照；候选人停用后仍可回看历史。
- `rm_demand_notice.step_no` 按级去重审批消息；同一人跨级会收到不同级的消息，本级完成后旧消息置已读。

## 三、状态机

```text
NONE：提交 → approval_status=NONE，无步骤 → 现有处理待办

DIRECT/HIERARCHY：
  提交
    → 生成有主管的步骤：第一级 PENDING，其余 WAITING
    → 第一级存在候选人：approval_status=PENDING，approval_step=第一级
    → 整条链无候选人：approval_status=NONE，直接进入现有处理并写时间线
  当前级通过
    → 当前级 APPROVED
    → 有下一级：下一级 PENDING，approval_step 前移，需求仍 PENDING
    → 无下一级：approval_status=APPROVED，进入现有处理，通知填报人与单据管理员
  当前级驳回
    → 当前级 REJECTED，后续 WAITING → SKIPPED
    → approval_status=REJECTED，通知填报人，不通知单据管理员
```

- `PENDING` 与 `REJECTED` 不进入普通待办、只收集未读和追问待办；`PENDING` 只出现在当前级候选人的「待我审批」。
- 处理动作在 `PENDING` 返回 409「需求待部门主管审批」，在 `REJECTED` 返回 409「需求审批未通过」。
- 审批通过后 `public_version` 才递增；中间级不产生填报者未读。

## 四、审批链与候选人

- 直属主管：按填报人有效部门排序（`sort_no,name`），取第一个能产生步骤的部门；该部门全部在职主管（排除填报人）为第 1 步候选人。若该部门无主管，继续尝试填报人的下一个部门；都不行则不启动审批。
- 逐级审批：以同样的部门顺序取第一个能产生步骤的部门，从该部门沿 `parent_key` 向上遍历所有上级，包含根部门；每级有效主管（排除填报人）非空才生成步骤；无主管的部门不生成步骤。
- 主管规则：`rm_demand_dept_leader` 为主；读取时过滤停用账户；`rm_demand_dept.leader_id` 作为旧数据回退。
- 自动排除填报人本人；某级只剩填报人本人时该级跳过。
- 多部门填报人：只选一个起点部门，不做多部门并行审批；DIRECT 可顺延到下一个有主管的部门，HIERARCHY 选第一个能产生步骤的部门后不再切换。
- 根部门（瑞玛电气）当前无主管时自然跳过；若以后设置根主管，会成为最后一级。
- 部门主管由用户在「用户管理」页设置，支持多选；审批人不需要额外平台权限。

## 五、接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/demand-api/requests?scope=approval` | 当前级待我审批列表，含当前级、部门、候选人 |
| GET | `/demand-api/requests/summary?scope=approval` | 待我审批按收集单汇总 |
| POST | `/demand-api/requests/{id}/approval` | body `{decision:'APPROVE'\|'REJECT', comment, revision}` |
| GET | `/demand-api/requests/{id}` | 返回 `approvalStatus/approvalMode/approvalStep/approvalSteps/canApprove/approvalLeaderName` |
| POST | `/demand-api/admin/forms/{key}` | 收集配置增加 `approvalMode`，兼容 `requiresLeaderApproval` |
| PUT | `/demand-api/admin/departments/{key}` | body 支持 `leaderIds` 数组，兼容 `leaderId` |
| GET | `/demand-api/admin/departments` | 返回 `leaderIds/leaders/leaderNames` 与兼容字段 |
| GET | `/demand-api/capabilities` | `approvalPending` 与 `approver` |

规则：

- 审批接口使用需求行锁、步骤行锁与 `revision` 乐观锁；重复审批、已被同级他人处理返回 409，非当前候选人返回 403。
- `approvalSteps` 每项为 `{stepNo,deptKey,deptName,status,comment,actedBy,actedByName,actedAt,approvers:[{userId,name}]}`。
- 处理接口 `assign/outcome/reply/followUp/publish/autoPublish/skip` 在处理前校验聚合状态。
- 删除需求时清理步骤、候选人和通知；收集单彻底删除时清理无孤儿步骤。

## 六、页面

- 收集配置：「审批方式」单选（不审批/直属主管审批/逐级审批），选择非不审批时自动关闭匿名；表单卡片显示「主管审批/逐级审批」标签。
- 用户管理：部门主管改为多选，展示「主管 A、B/主管 A 等 2 人」；按用户卡片显示每个部门的主管标签。
- 待我审批：列表显示当前级、部门与候选人；隐藏无关的经办/采纳/进度列；同一级任一主管通过即可。
- 详情：顶部审批三态提示；「审批记录」逐级展示状态（待审批/未开始/已通过/已驳回/已跳过）、意见、处理人、时间；`canApprove` 时显示当前级操作，非当前级只读。
- 我的需求：显示「待审批/已驳回」；填写回执按模式提示「等待部门主管审批/等待逐级审批」。
- 消息中心：审批任务显示级别；点击进入待我审批，结果消息进入我的需求。

## 七、通知

- 提交：只通知当前级全部候选人（`APPROVAL`，按需求 + 级去重）；不通知单据管理员。
- 中间级通过：本级全部审批消息置已读，通知下一级候选人；不通知填报人和单据管理员。
- 最终通过：通知填报人 `APPROVAL_RESULT`，通知单据管理员 `NEW_DEMAND`；`public_version` 递增。
- 驳回：通知填报人 `APPROVAL_RESULT`（含驳回意见）；不通知单据管理员。
- 整链无主管：写时间线「未配置部门主管，需求直接进入处理」，通知单据管理员 `NEW_DEMAND`。
- 钉钉后续按事件类型接入，站内消息仍是唯一事实来源。

## 八、边界与风险

- 匿名：审批模式非 `NONE` 时拒绝匿名提交；存量匿名需求不追溯。
- 只收集：可配置审批；最终通过后进入只收集未读待办，驳回不进入。
- 在途：提交时固化步骤与候选人；组织调整不影响在途；历史 PENDING 单级需求由迁移回填为一步。
- 人员停用：提交和下一步激活时只取在职候选人；若当前级全部停用，需求会暂时无人可审，作为已知风险；后续可增加转交或管理员代审。
- 多部门：只选一个起点部门；如需要固定主部门，后续可增加主部门字段。
- 重新提交：驳回后需求终止，暂不支持修改重提。
- 兼容：`leader_id`、`requiresLeaderApproval`、`approval_leader_id/comment/at` 保留；旧前端或旧后端回滚可用。

## 十、默认值

1. 同一级多主管：或签，任一通过即可。
2. 逐级：到所有上级部门；无主管部门跳过；整链无主管直接进入处理。
3. 多部门：按 `sort_no,name` 取第一个能产生步骤的部门；DIRECT 可顺延，HIERARCHY 不切换。
4. 驳回：任一级终止，后续未开始步骤标记已跳过，不通知单据管理员。
5. 审批通过：不自动分派经办人，仍由单据管理员处理。
6. 技术中心细分：赵仁磊归电气；技术中心/机械/电气主管由用户设置。
